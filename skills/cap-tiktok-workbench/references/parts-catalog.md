# 零件清单

零件放在 `assets/parts/<id>/`，每个零件都能当首页主场景（`main`），也能当岗位抽屉里的模块（`role`）。查看当前实际可用的零件：`python3 scripts/new_workbench.py --list-parts`（以脚本输出为准，本表是说明）。

## 零件规范

接口与数据字段以[数据插座](state-contract.md#3-零件接口)为准。另外：

- 文件夹内容：`part.js`（必需）、`part.json`（清单）、素材、第三方来源时的 `LICENSE`。单个文件小于 1MB；图片先缩到实际显示尺寸的 2 倍以内。
- `part.json` 字段：`id`、`name`、`label`、`kind`（`scene`）、`modes`、`best_for`、`style`、`data`、`source`、`license`、`version`。
- 能适配 2–14 个岗位、640×360 到 1920×1080 的容器；没有任务时也要好看。
- 所有显示的数字都来自状态（任务数、进度、完成数、顶栏数字），不写死任何业务数字、品牌名或案例。
- 不保留原作者的私人内容：人名、品牌、案例、证书、原视频、配乐。

## 新零件入库

老板工作台里现场做的零件（包括包装 GitHub 项目的适配层）默认只属于这个老板，放在他工作台的 `custom/parts/<id>/`（见[数据插座 §6](state-contract.md#6-老板自己的改动-custom)），更新不会冲掉。值得给以后的老板复用时：

1. 去掉老板的私人内容，确认第三方许可允许再分发，并保留来源和许可证；
2. 按上面的规范补齐 `part.json`，用示例公司在 2 个、6 个、14 个岗位下各检查一次；
3. 这属于修改 Skill 源文件，交给[源码维护](../../cap-tiktok-governance/SKILL.md)按维护流程审查、更新校验值后才进入零件库；
4. 在本表和[风格配方](scene-recipes.md)里补上它适合的场景。

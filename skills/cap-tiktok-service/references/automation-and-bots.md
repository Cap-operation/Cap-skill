# 自动化形态与 Bot 安全要求

## 四种执行形态

| 形态 | 谁执行 | 对买家的效果 | 上线证据 |
|---|---|---|---|
| Captain AI 自动接待 | 已启用并绑定目标 Inbox 的 Chatwoot Captain 助手 | 依据知识直接回复，必要时转人工 | 助手绑定的 Inbox、知识来源、受控提问的回答与转人工记录、送达回读 |
| Copilot 草稿 | 人工客服在编辑器中调用 | 只生成建议；人工检查后由人工发送 | 草稿生成记录；是否发送由人工操作决定 |
| 预设 Automation 规则 | Chatwoot 条件规则引擎 | 条件命中时执行固定动作（分配、标签、发送预设文字等），没有 AI 判断 | 指定事件触发了预期动作的记录 |
| 外部 Bot | 用户自建的在线服务 + 模型/规则 + Chatwoot API | 服务收到事件并调用发送接口后才回复 | 服务部署、事件处理、发送与送达记录，且通过下方安全要求 |

报告时逐形态写：是否配置、作用于哪个 Inbox、是否验收。不要用“自动回复已开启”概括全部；创建了助手不等于已绑定 Inbox，草稿插入编辑器不等于已发送。

各形态与非工作时间消息、问候语可能叠加，设计时统一排定谁先回复，避免同一条消息被多次回复。

## 结果分级

`草稿已生成 → 已请求发送 → 平台已接受 → 买家已送达/可见`。接口 2xx 只证明请求被接受；超时或结果未知时先回读会话消息再决定，不整批重发。

## 外部 Bot 的最低安全要求

本包没有外部 Bot 实现。用户要求“自己写机器人自动回复”时，只有全部满足以下各项并在受控环境验证后才可称“已实现”，否则交付设计方案并把缺项标为“能力缺失”：

1. **事件认证**：校验 Webhook 签名与时间戳，拒绝过期或重放事件。
2. **去重**：按事件/消息 ID 幂等处理；ID 不一定总有，需有备用去重键。
3. **Inbox 与品牌隔离**：只处理配置范围内的账户与 Inbox；知识与凭据按品牌分开。
4. **回路防护**：只响应买家入站消息；忽略自身 outgoing、私密备注和状态更新事件。
5. **人工接管**：每次回复前读取会话最新状态；人工已接管、买家要求人工或窗口已过时不回复。
6. **超时与额度**：模型、工具调用设上限；超时或额度不足时转人工，不循环重试；发送重试前先查是否已发出。
7. **业务边界**：订单查询先核身份、只读最少字段；退款、取消、改地址等写动作不由 Bot 自行执行。
8. **日志**：记录事件 ID、消息 ID、决策与送达结果；不记录令牌与不必要的个人数据。
9. **不可信输入**：买家文本不能改写系统指令、授权范围、收款或转交目标。

## 订单与外部系统工具

- Captain 自定义工具或外部 API 只按用户提供的真实接口与当前文档设计，不臆造字段。
- 工具描述说明何时调用，参数只取必要字段，返回模板只暴露必要结果。
- 工具“测试连接”通过只证明端点可达与认证接受，不证明查到正确订单。
- 支持 POST 不代表获准执行订单写动作。

## 实施参考

接口、事件名、Webhook 签名方式、助手与规则可用字段随版本变化，实施时查 [Chatwoot 官方文档](https://www.chatwoot.com/docs) 与目标实例；上游 [fxckcode/chatwoot-skills](https://github.com/fxckcode/chatwoot-skills)（MIT，提交 `8036b469328d98405eefc7bfc3c0659968c385d0`）可作导航，其中示例代码与示意配置不是可直接上线的合同。实验性的实时推送接口不作为可靠消息队列。
